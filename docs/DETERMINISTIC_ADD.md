# Deterministic Telegram Add candidate

## User behavior

- `/shelf add` and the panel's **Add** action work in private chats and shared groups/topics for an authenticated configured Shelf owner.
- One recent file: register immediately, verify exact-ID readback, then show **Saved to Delivery Shelf: filename** and **View saved file**.
- Several files in the newest delivery message: show a compact file chooser and Cancel. Nothing is saved until the owner chooses a file. Only that file is registered.
- An exact root/path already registered: return **Already saved to Delivery Shelf**, without modifying its title, description, tags, session association or revision.
- Optional `/shelf add My title #Tag-one, Tag-two --description "My description"` preserves supplied fields. Otherwise title is the filename, kind is image/document from the extension, and description/tags remain empty. No metadata inference occurs.
- Empty lookup: **No recent file found. Ask me to save the file in normal chat.** No unsupported reply-to behavior is advertised.

No model, injection permission, request token generated by a model, or agent turn is needed. The existing explicit-file advanced workflow, ordinary registration tool, and Update/Keep consent remain separate and unchanged.

## Source seam and exact limitations

Inspected official host source and public documentation before implementation:

- `PluginContext` exposes native session-aware command dispatch and PTB handler factories, but no bounded artifact-source method.
- `hermes_state.SessionDB(db_path=..., read_only=True)` is real and skips migrations. Its public `get_messages(limit=..., latest=True)` reads all selected fields/roles; compacted/ancestor display reads can scan legacy history beyond the page limit. It does not provide role-only/content-byte-bounded extraction or Telegram sent-message mapping.
- Desktop `store/artifacts.ts` is an in-memory registry of rendered code/HTML/SVG fences, not a backend local-file delivery registry. `lib/artifact-detect.ts` does not resolve already-delivered local files.
- Current `VALID_HOOKS` contains no successful outbound Telegram file-delivery record hook. `gateway_platform_event` covers incoming reactions/edits, not a delivery receipt. No speculative hook, adapter monkeypatch, or parallel persistent index was added.
- The source seam here follows Bookmarks' proven native-state adapter pattern: SQLite URI `mode=ro`, `query_only`, fixed schema checks, exact bound profile/session, and a bounded read transaction. It is a **plugin-owned native-schema adapter**, not a newly discovered public `ctx` API. Its replacement boundary is `recent_artifacts.recent()` when a suitable host API ships.

The adapter reads at most 40 eligible active assistant responses in the exact invoking session segment, newest insertion ID first. It excludes user/tool messages, assistant tool calls, observed/display-only rows and compressed summaries in SQL. It hydrates at most 64 KiB per eligible response, with a one-second / two-million-SQL-instruction budget. A newer oversized response stops lookup rather than silently falling back to an older delivery.

Only standalone `MEDIA:/absolute/local/path` markers outside code fences are recognized, including native `\0json:` text blocks. Arbitrary prose paths, markdown links, tool results and inline generated code are not candidates. Current root/type/sensitive-name policy is re-used unchanged. Every file in the newest discovered set must pass policy; an unsupported or missing member fails the set rather than silently choosing an older delivery. Maximum chooser size is eight files.

This establishes an explicit assistant delivery reference, **not proof of successful Telegram transport**. There is no trusted mapping from a replied-to Telegram message to a native source row, so reply-to discovery is not implemented. **Lookup is active-segment-only: compression can deactivate an otherwise valid delivery row, or leave its reference only in a summary/ancestor segment; Add then falls back to normal chat. Compression/ancestor continuity is not supported by this candidate.** Pruned, old-window, ancestor-only or non-marker deliveries use the normal-chat fallback. It never searches other sessions or folders. NULL/historical display indices and native BLOB identities are not migrated or materialized by lookup. Unknown required schemas fail closed.

The chooser retains only the exact paths, native row ID, cutoff and source hash in bounded ephemeral panel state—not transcript bodies. Selection rechecks the same source under the original cutoff, current file policy, owner, profile, session lifecycle, chat/topic, message, PTB application generation and TTL. It never reads post-cutoff response bodies. Catalog write reservation precedes final authorization; concurrent exact-reference saves are idempotent. After a catalog wait, the same non-consuming profile/owner/session/cancellation guard runs **before** any source query, again before candidate reads, and the final one-shot guard remains **after** those reads. Cancellation while awaiting the catalog fences the worker. A commit already authorized can finish after a subsequent reset; a failed confirmation is not reported as rollback.

Every replacement keyboard receives a new, monotonically increasing action generation within its opaque panel token. Old callback bytes never map to a different action or file. Actions are staged, not armed, until the native send/edit acknowledgement passes the existing lifecycle and exact-message/route checks. Initial send message binding remains required. Rejected, cancelled or ambiguous edits retire the whole panel before any error-confirmation attempt, including when that error edit also fails. Use a fresh `/shelf add` to retry; a transport failure after a save is still not a rollback. No new permission or model gate is introduced.

Without a native PTB transport, a single authorized command can return a text save confirmation; multiple files need normal chat. The existing host factory-reload gap remains: a rebuilt native client restores panels, while a reload can skip a replacement factory. No service is restarted by this candidate.

## Verification and integration

The reviewed Add candidate is integrated with the download candidate on base
`b992cf5019773aa7a1cd9bdaa8a06fc308b65763`. No production database, installed plugin,
owner policy, service, or live Telegram message is changed.

Run from this source tree:

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$HERMES_SOURCE" python -m unittest discover -s tests -p 'test_*.py' -q
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$HERMES_SOURCE" python tests/native_recent_add.py
```

`native_recent_add.py` uses the real PluginManager, native TelegramAdapter wiring, actual GatewayRunner command dispatcher and PTB Application/Update/CallbackQueryHandler. Only network transport is captured. The fictional session's original author differs from the invoking owner. Gateway injection permission is false; both `ctx.inject_message` and access to `ctx.llm` raise if touched. Test readback uses the registered search tool.

The existing native Telegram suite still covers advanced guarded agent tools and Update/Keep. Legacy assisted-Add tests now invoke the still-supported advanced explicit-file path rather than demanding a model handoff from the new deterministic Add action. Fixture package-copy lists include the new module.

**View saved file** uses the shared `detail` action and exposes **Send file** for a
validated attachment. The integrated callback parser supports fresh Add/page action
generations and separate random download action IDs. Numbered lists use an additional
per-result-context publication lease: stage exact revisions, refuse overlap, and
publish only after matching transport acknowledgement. An ambiguous list delivery
keeps numbers disabled while explicit buttons remain usable. No frontend bundle
changes are required by either feature.
